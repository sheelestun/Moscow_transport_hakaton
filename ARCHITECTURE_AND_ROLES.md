# Архитектура и роли

Проект: **Предиктор изменений в графике движения городского транспорта** (хакатон Московского транспорта).

Задача — ИИ-система, которая по потоковой телеметрии NDTP за **10–15 минут** до фактической задержки предупреждает диспетчера и рекомендует упреждающее действие.

---

## 1. Что мы строим

Три независимых сервиса, поднимаются одним `docker-compose`:

- **ML-модуль** — обучение офлайн, инференс онлайн, ансамбль CatBoost + PyTorch, экспорт в ONNX.
- **Backend** — приём NDTP-потока из эмулятора, склейка с расписанием, фиче-стор, оркестрация, REST/WebSocket API, логика алертов.
- **Frontend (BI-дашборд)** — карта Москвы с маршрутами и ТС, лента алертов с рекомендациями, панель What-if.

Плюс общие: Redis (онлайн-фичи, шина), Postgres (история и алерты).

---

## 2. Ограничения (что можно / что нельзя)

**Обязательно:**
- Стек: **Python 3.12+, PyTorch, CatBoost, Docker**. Другие ML-фреймворки не используем.
- Горизонт прогноза строго **10–15 минут**.
- ML и Backend — **разные сервисы** (не монолит).
- UI ориентирован на **действие диспетчера**, а не на «показать всё подряд».
- Внешние API (Яндекс.Пробки, погода) — разрешены, интернет на демо-стенде есть.

**Не подходит:**
- LightGBM / XGBoost / TensorFlow / JAX — вне стека.
- Kafka — избыточно для 48 часов, берём Redis Streams или NATS.
- Своя реализация парсинга сырого NDTP — используем эмулятор оргов и его выход.

**Инфраструктура:** серверы **НЕ дают**. Хостим сами (VPS команды).

---

## 3. Команда и зоны ответственности

| Кто | Роль | Владеет |
|---|---|---|
| **Степан** | ML | Sequence-модель (PyTorch/Transformer), ансамбль, инференс-сервис |
| **Фёдор** | ML | Табличная модель (CatBoost), фиче-инжиниринг, экспорт ONNX |
| **Даниил Герман** | Backend | Ingestor NDTP, шина, feature store, API, алерты, docker-compose, деплой |
| **Вероника** | Frontend / BI | Дашборд диспетчера, карта, live-обновления, панель What-if |
| **Даниил Шелестов** | Data Analyst / DBA | EDA, качество данных, склейка расписания и телеметрии, схема Postgres, метрики |

**Матрица «кто с кем договаривается в первый час»:**

- Backend ↔ ML — **контракт `/predict`** (поля запроса и ответа).
- Backend ↔ Frontend — **контракт API + WebSocket-событий**.
- Data Analyst ↔ ML — **схема тренировочного датасета и таргета** (что считаем «задержкой»).
- Backend ↔ Data Analyst — **схема Postgres**.
- Все — **общий словарь полей** (id ТС, id маршрута, id остановки, timestamp UTC).

Если задача на стыке — владелец тот, чей сервис хранит конечный артефакт.

## 4. Архитектура

```
┌────────────────────────┐
│  NDTP-эмулятор (orgs)  │  docker-образ от оргов
└──────────┬─────────────┘
           │ поток NDTP
           ▼
┌────────────────────────┐
│  Ingestor + Parser     │  backend, парсит по схеме,
│                        │  проставляет timestamp UTC
└──────────┬─────────────┘
           │ нормализованные события
           ▼
┌────────────────────────┐       ┌──────────────────────┐
│  Redis Streams (шина)  │◀─────▶│  Расписание (CSV)    │
└──────────┬─────────────┘       │  + геометрия маршрут.│
           │                     └──────────────────────┘
           ▼
┌────────────────────────┐
│  Map Matching          │  снап GPS на маршрут,
│  + Schedule Join       │  расчёт текущего отклонения
└──────────┬─────────────┘
           │
           ▼
┌────────────────────────┐       ┌──────────────────────┐
│  Feature Store (Redis) │──────▶│  ML Inference Service│
│  online-фичи по ТС     │       │  PyTorch + CatBoost  │
└──────────┬─────────────┘       │  ONNX Runtime        │
           │                     └──────────┬───────────┘
           │                                │ delay_pred, risk
           │                                ▼
           │       ┌─────────────────────────────────────┐
           └──────▶│  Backend API (FastAPI)              │
                   │  правила алертов (порог+дедуп),     │
                   │  What-if оркестрация,               │
                   │  REST + WebSocket                   │
                   └──────────┬──────────────────────────┘
                              │
                              ▼
                   ┌──────────────────────┐   ┌───────────────────┐
                   │  Frontend BI         │   │  Postgres         │
                   │  карта, алерты,      │   │  история, алерты, │
                   │  What-if             │   │  метрики модели   │
                   └──────────────────────┘   └───────────────────┘
```

### Почему так, а не иначе

- **ML отдельным сервисом** — прямое требование оргов + можно перекатывать модель без деплоя бэка.
- **Redis Streams, а не Kafka** — поднимается за 5 минут, справится с одним эмулятором, экономит нам сутки времени.
- **Feature Store на Redis** — онлайн-фичи (текущее отклонение, headway, скорость) должны отдаваться за миллисекунды.
- **Map Matching отдельным шагом** — тяжёлая операция, кэшируется по сегменту маршрута, а не по ТС.
- **Postgres на историю** — бэку не приходится ходить в два стора; для 48 часов SQLite тоже вариант, если Postgres не поднимется быстро.
- **Один VPS + docker-compose** — на демо один хост, все сервисы рядом; масштабируемость показываем схемой, а не реальным k8s.

## 5. Контракты между сервисами

Согласовать в первый час, потом фиксируем и не меняем без всех.

### 5.1 Backend → ML: `POST /predict`

```json
// request
{
  "vehicle_id": "12345",
  "route_id": "A-905",
  "timestamp": "2026-09-27T10:15:00Z",
  "features": {
    "current_delay_sec": 42,
    "speed_avg_5min": 18.3,
    "headway_to_next_sec": 380,
    "headway_to_prev_sec": 210,
    "segment_id": "seg_045",
    "dwell_last_stop_sec": 25,
    "hour_of_day": 10,
    "day_of_week": 4,
    "weather_code": 2,
    "traffic_score": 0.7,
    "history": [
      {"t": -60, "lat": 55.75, "lon": 37.61, "speed": 15},
      {"t": -55, "lat": 55.751, "lon": 37.611, "speed": 20}
      // ... окно последних N пингов
    ]
  }
}

// response
{
  "vehicle_id": "12345",
  "horizon_min": 12,
  "delay_pred_sec": 187,     // главный таргет, MAE считается по этому полю
  "risk_score": 0.83,        // производный от delay_pred_sec, для UI (0..1)
  "confidence": 0.71,        // опционально: 1 - нормированная дисперсия ансамбля
  "top_features": [          // для объяснения на дашборде
    {"name": "current_delay_sec", "contribution": 0.42},
    {"name": "traffic_score", "contribution": 0.18}
  ],
  "model_version": "ens-0.3.1"
}
```

Двойной выход (`delay_pred_sec` + `risk_score`) закрывает расхождение между слайдом «вычисляет вероятность» и метрикой MAE: обучаем регрессию на секунды, `risk_score` = детерминированная функция от предсказания (например, `sigmoid((delay_pred - 120) / 60)`), никакой второй модели не нужно.

### 5.2 Backend → Frontend

REST:
- `GET /routes` — список маршрутов и геометрия.
- `GET /vehicles?route_id=…` — текущие ТС на маршруте.
- `GET /alerts?active=true` — активные алерты.
- `POST /whatif` — сценарий: `{scenario: "add_reserve", route_id, at_stop_id}` → пересчитанные прогнозы.
- `GET /metrics/model` — свежий MAE по последнему часу (для аналитика и демо).

WebSocket `/ws`:
```json
// событие "alert.new"
{
  "type": "alert.new",
  "alert_id": "a-91021",
  "vehicle_id": "12345",
  "route_id": "A-905",
  "segment_id": "seg_045",
  "delay_pred_sec": 187,
  "risk_score": 0.83,
  "eta_incident": "2026-09-27T10:27:00Z",
  "reason_pattern": "traffic_jam_ahead",
  "recommendation": "release_reserve"
}
```

### 5.3 События в шине (Redis Streams)

- `telemetry.raw` — сырые события от ingestor.
- `telemetry.matched` — после Map Matching, обогащённые segment_id и текущим отклонением.
- `predictions.new` — прогнозы, публикуются ML.
- `alerts.new` — алерты после логики порогов + дедупа.

Frontend подписан на `alerts.new` через WebSocket-мост в бэке.

## 7. Фазы работы (48 часов условно)

**Фаза 0 — Kickoff (первый час после старта):**
- Разбираем полное ТЗ и материалы эмулятора все вместе.
- Согласовываем контракты из раздела 5 и словарь полей.
- Даниил Ш. запускает EDA, остальные готовят каркасы своих сервисов.

**Фаза 1 — MVP end-to-end (первые ~8 часов):**
- Ingestor читает эмулятор и кидает в Redis Streams.
- Простой Map Matching (nearest-stop snap, без OSRM).
- Feature Store с 5–7 базовыми фичами.
- CatBoost baseline от Фёдора отдаёт `/predict` (константа или простая модель).
- Backend публикует моковый алерт в WebSocket.
- Frontend показывает карту и одну ленту алертов.
- **Цель фазы: сквозной поток данных работает, MAE считается.**

**Фаза 2 — Итерация качества (следующие ~20 часов):**
- Степан поднимает sequence-модель на PyTorch.
- Фёдор дожимает CatBoost, добавляет внешние фичи (погода, пробки).
- Ансамбль.
- Даниил Г. дописывает логику алертов (пороги, дедуп) и What-if.
- Вероника — тепловая карта риска, панель What-if, объяснения по `top_features`.
- Даниил Ш. — витрины метрик, проверка качества склейки.

**Фаза 3 — Hardening (следующие ~12 часов):**
- Экспорт в ONNX, измерение latency до/после (для баллов за оптимизацию).
- Настоящий Map Matching (Valhalla/OSRM) — **только если есть время**.
- Стабилизация UI, edge-кейсы (пропали данные по ТС, эмулятор упал).
- Прогон нагрузочного теста на записанном трафике.

**Фаза 4 — Демо (последние ~8 часов):**
- Скрипт демонстрации: сценарий с явной задержкой, показ алерта за 10–15 мин, диспетчер жмёт «выпустить резерв», What-if пересчитывает.
- Метрики на слайд: MAE по маршруту, latency инференса до/после ONNX.
- Резервный VPS + локальный ноутбук как fallback.

## 8. Что нужно уточнить, когда придут материалы

Первым делом проверяем в описании задачи и эмуляторе:

1. **Транспорт эмулятора:** TCP/UDP/gRPC/HTTP → определяет ingestor.
2. **Частота пингов:** 1 Гц / 5 сек / 30 сек → определяет размер окна и глубину sequence-модели.
3. **Поля NDTP:** только GPS+скорость или ещё двери, пассажиропоток, номер маршрута.
4. **Формат таргета в трейне:** уже размеченные задержки на 10–15 мин или считаем сами.
5. **Геометрия маршрутов:** polyline или только последовательность остановок → нужен ли настоящий Map Matching.
6. **Как оценивают на приватке:** прогоняют эмулятор от старта или подсовывают свой сегмент.

Пока не ответили — не пилим ingestor и Map Matching «на глазок».

## 9. Бонусные фичи (за них дают баллы)

Порядок реализации по стоимости/выгоде:

1. **Ансамбль CatBoost + PyTorch/Transformer** — прямо просят на слайде, у нас 2 ML.
2. **Map Matching с учётом NDTP-специфики** — если хватает времени в Фазе 3.
3. **Оптимизация инференса** (ONNX Runtime + INT8 квантизация) — быстро, дёшево, обязательно замерить latency до/после и показать на слайде.
4. **What-if** — уже в MVP как минимум для сценария «выпуск резерва»; глубже — если Фаза 3 закрыта.
5. **TensorRT** — только если демо на GPU и очень хочется красивую цифру. Иначе не тратим время.

## 10. Метрики и что показываем на демо

**Модельные:**
- MAE по величине задержки (главный, на этом судят).
- MAE в разрезе: маршрут / час дня / погода / severity.
- Precision/Recall алертов на пороге риска (для читаемости на UI).

**Системные:**
- Latency инференса p50 / p95 (до и после ONNX).
- End-to-end latency: пинг эмулятора → алерт в UI.
- Пропускная способность ingestor (пингов/сек).

**UX-демо:**
- Диспетчер видит риск за 10–15 мин.
- Одним кликом смотрит объяснение (`top_features`).
- Прогоняет What-if «а если выпустить резерв» → видит дельту.

## 11. Definition of Done по ролям

**ML (Степан + Фёдор):**
- `/predict` работает в отдельном контейнере, отвечает <200мс p95.
- Ансамбль обучен, MAE зафиксирован на валидации.
- ONNX-экспорт готов, latency замерен до/после.
- Контракт с бэком не меняется без объявления.

**Backend (Даниил Г.):**
- `docker-compose up` поднимает весь стек одной командой.
- Ingestor держит поток без падений >1 часа.
- Все API из раздела 5 отвечают.
- Алерты не дублируются (дедуп на уровне ТС+инцидент).

**Frontend (Вероника):**
- Карта Москвы с маршрутами и живыми ТС.
- Лента алертов обновляется по WebSocket.
- Панель What-if вызывает бэкенд и рендерит результат.
- Дизайн читается на проекторе с 3 метров.

**Data (Даниил Ш.):**
- Отчёт по качеству данных сдан к концу Фазы 1.
- Схема Postgres развернута, миграции в `data/sql/`.
- Витрина `GET /metrics/model` наполняется.
- Метрики для демо-слайда посчитаны и проверены.

## 12. Риски и что с ними делать

| Риск | Митигация |
|---|---|
| Эмулятор шлёт данные в непонятном виде | Ingestor пишем адаптером, парсер меняем без трогания шины |
| Расписание и телеметрия не склеиваются по ключу | Data Analyst валидирует склейку в Фазе 0, до старта Фазы 1 |
| ML не успевает обучиться | Всегда держим CatBoost baseline как fallback, ансамбль — сверху |
| VPS падает на демо | Держим второй VPS + локальный запуск на ноуте с ngrok |
| Frontend не успевает | Минимум — карта + лента; What-if вырезаем в первую очередь |
| Кто-то заболел / отвалился | Backend ↔ Data Analyst и ML1 ↔ ML2 частично взаимозаменяемы, задачи разбиваем на самодостаточные PR |
